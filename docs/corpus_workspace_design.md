## 1. 核心判断

### 1.1 写面已有架构，读面只有零件

| 面 | 现状 | 证据 |
|---|---|---|
| 写面 | 有完整管线 | `office_core/runner.py` 九步（选文件→scan→plan→确认→preflight→快照→execute→verify→证据） |
| 写面 | 三个格式到位度不一 | word 2490 行 / text 359 行 / excel 21055 行（查询非写回） |
| 读面 | **只有零件，无骨架** | `stage1_parser/file_parser.py`（抽取）+ `stage3_processor/ai_caller.py`（分析）+ `_db_query` 的 LIKE 三表 |
| 读面 | 记忆碎片 4 套 | `word memory.py` / `block_cross_table/memory_rag` / 两套 `session` / `db/choice_memory` |

**结论**：不为新格式再开一个"重写版"项目。但可以按 **写面 / 读面** 拆成两个仓库——因为这两条线本来就只在 `corpus.read()` 一个点上相接（详见 §12）。

### 1.2 格式差异只存在于 extract 一步

```
docx  ─┐
pdf   ─┤
图片  ─┼──→ extract ──→ 纯文本 + 出处 ──→ 切块 / 索引 / 检索 / 分析 / 回答
音频  ─┤                                    （全部共享，只写一遍）
视频  ─┘
```

过了 `extract`，一切都与格式无关。所以：**加一个格式 = 加一个 `extract()`，下游全免费。**

### 1.3 迭代学习 = 语料 + 检索 + 纠正 + 评测，不是模型权重

| 角色 | 是什么 | 谁最适合 | 要不要本地 |
|---|---|---|---|
| 眼睛 | 图片 → 文字 | OCR（1~2 亿参数） | 本地 |
| 耳朵 | 音视频 → 文字 | Whisper | 本地（或云 ASR） |
| 记性 | 存文字 / 切块 / 索引 / 术语 / 纠正 | SQLite + FTS5 + 向量 | 本地 |
| 大脑 | 理解、回答、改写 | 大语言模型 | 云（主）/ 本地（备） |

**本地部署的是"感官"，不是"记性"。记性在库里，不在权重里。**
模型不学习，库学习。加资料、加纠正 → 检索变准，全程不需要重训。

**文本不属于"感官"**：`.txt/.md/.json` 用 Python 直接读，**不需要任何模型**。别为它部署模型。

**不做微调**：加一批资料要重训、不能引用原文、改完无法验证、个人量级（几千块）RAG 严格更强。

### 1.4 "迭代学习"和"整体融合"是同一件事

迭代学习需要三样：统一读接口、共享库、写后重建索引。这三样本身就是"融合"的载体。
**所以待办不是两条，是一条：建库。**

## 2. 格式三类（A / B / C）

不是按"轻重"分，是按 **改坏了会毁什么** 分。

| 类 | 格式 | 能改什么 | 改坏了毁什么 | 门禁 | 加格式成本 |
|---|---|---|---|---|---|
| **A 只读** | 视频 / 音频 / 图片 | 不改原文件 | 不毁 | 无 | 一个 `extract()` |
| **B 结构改** | PDF | 页（删 / 转 / 拆 / 合） | 页序、文件本身 | 快照 + 确认 | 一个页 adapter |
| **C 内容改** | word / excel / txt | 文字 / 单元格 / 字符 | **内容本体** | 契约 + 门禁 + 快照 + 回滚 | 一个 `word_office` 级 |
| D 只读（暂定） | PPT | 只有抽取 | — | — | 做成 C 等于再造 `word_office` |

一句话：**A 是感官，B 是整理，C 是手术。三个手术台不一样，别共用。**

### 2.1 两处归类修正

- **PDF 不是 A**：Word 能改"违约金"三个字，PDF 改不了；但 PDF 能删第 3 页。**内容不可改、结构可改。** 若一年内不做页操作，可临时按 A 处理——这是选择，不是属性。
- **PPT 不是 C**：现状只有 `_pptx_to_text`。**建议永远只读**，"改 PPT"的成本约等于重做 `word_office`。

## 3. 三个轴正交，别用一个轴解另一个轴的问题

| 轴 | 回答什么 | 取值 |
|---|---|---|
| **格式** | 怎么进来的 | docx / pdf / txt / xlsx / image / audio / video |
| **层** | 结构上放哪 | source / chunk / vec / semantic / interaction |
| **空间** | 归哪个领域 | 八字 / 小说 / 人际 / 默认 |

格式的差异在库里只出现三处：`source.kind`、`source.meta`、`chunk.locator`。其余全部与格式无关。

## 4. 三件事：投料 / 问答 / 操作

### 4.1 唯一判据：**谁的状态被改变**

| | **投料** | **问答** | **操作** |
|---|---|---|---|
| **改变什么** | **库** | **什么都不改** | **文件**（顺带改库，靠 reindex） |
| 有状态吗 | 有（库变厚） | 无 | 有（文件变了） |
| 失败后果 | 可撤销（按批次） | 无（答错重问） | **不可逆** |
| 频率 | 低（每天几次） | 高（每天几十次） | 中 |
| 需要人陪吗 | 不需要（后台跑） | 需要 | 危险的要确认 |

三件事互不重叠，因为它们**各自只碰一个东西**：

- 投料 → 只碰库
- 问答 → 只读，什么都不碰
- 操作 → 只碰文件（然后触发 `reindex`，间接碰库）

### 4.2 连起来是个环

```
        投料 ──────→ 库 ──────→ 问答
                     ↑            │
                     │            ↓
                  reindex ←──── 操作（产物）
```

**库是心脏**：投料是入口，问答是出口，操作是回路。

- 投料和问答**不共享代码**，只共享库；
- 操作改完文件必须 `reindex` 回库，否则库与文件不一致（改了合同违约金，问答还是旧数字）。

### 4.3 评测是竖线，不是第四个环节

```
投料 ──→ 库 ──→ 问答
  │                │
  └── 评测 ────────┘     ← 穿过投料和问答，本身不产生业务价值
```

评测**不进流程**，它横跨流程：查"投料有效吗"和"问答准吗"。详见 §7。

## 5. 库结构：一个 `.db`，8 张表

`db/corpus.db` — **必须是独立 SQLite 文件**，不能进业务库（业务库可切 MySQL，而 FTS5 / `sqlite-vec` 是 SQLite 专有）。

```sql
-- ① 空间
workspace(id INTEGER PRIMARY KEY,
          name TEXT UNIQUE,          -- 八字 / 小说 / 人际 / 默认
          config TEXT,               -- JSON：切块策略 / 模型 / 召回 k / 语气
          created_at REAL)

-- ② 批次（只用于撤销，不承载归属）
batch(id INTEGER PRIMARY KEY,
      note TEXT, created_at REAL, status TEXT)

-- ③ 源：每个文件一行，格式信息只在这里出现一次
source(id INTEGER PRIMARY KEY,
       workspace_id INTEGER REFERENCES workspace(id),
       batch_id INTEGER REFERENCES batch(id),
       path TEXT, kind TEXT, hash TEXT,
       size INTEGER, mtime REAL,
       meta TEXT,                    -- JSON：页数 / 时长 / 编码 / 分辨率
       indexed_at REAL,
       UNIQUE(path, hash))

-- ④ 块：正文只有这一份（格式无关）
chunk(id INTEGER PRIMARY KEY,
      source_id INTEGER REFERENCES source(id) ON DELETE CASCADE,
      ordinal INTEGER, text TEXT,
      locator TEXT,                  -- JSON：{"page":3} / {"line":120}
                                     --       / {"sheet":"S1","range":"A1:D9"}
                                     --       / {"t_start":372.5,"t_end":410}
      UNIQUE(source_id, ordinal))

-- ⑤ 全文索引：external content，不复制正文
chunk_fts USING fts5(text, content='chunk', content_rowid='id')

-- ⑥ 向量：只存向量（vec0 虚拟表只能有 id + 向量）
chunk_vec USING vec0(chunk_id INTEGER PRIMARY KEY, embedding FLOAT[1024])

-- ⑦ 记忆：两层共用一张表，workspace_id 为空 = 全局
memory(id INTEGER PRIMARY KEY,
       workspace_id INTEGER NULL,
       kind TEXT,                    -- term / correction / preference / conclusion
       key TEXT, value TEXT,
       source_ref TEXT,              -- 从哪次对话 / 哪个文件来
       status TEXT,                  -- active / invalidated / revoked
       at REAL)

-- ⑧ 引用：跨工作区的唯一合法通道
ref(id INTEGER PRIMARY KEY,
    from_kind TEXT, from_id INTEGER,
    to_kind TEXT,   to_id INTEGER,
    note TEXT, at REAL)
```

**对话表（`conv` / `msg`）下一轮加**，不阻塞建库。

### 5.1 三条"不乱"的规则

| 规则 | 反例 |
|---|---|
| 一个事实只存一处 | 正文既存 `source` 又存 `chunk` |
| 跨层只用 id 关联，不用路径字符串 | 用 `path` 当外键（文件改名即断） |
| 格式特有字段一律进 JSON，不新开列 | 为 pptx 加 `slide_count`、为 audio 加 `duration` |

### 5.2 "乱"的真正来源

不是"共用一个库"，是**同一个概念有多个定义**：

| 概念 | 现有名字 |
|---|---|
| 文件指纹 | `hash`（word memory）/ `file_hash`（choice_memory）/ `hash`（file_parser） |
| 文件路径 | `path` / `file` / `source_path` |

一张 schema 的价值 = 让"文件指纹"全项目只有一个意思。

## 6. 工作区

### 6.1 判据：按"以后你会一起问什么"分

| 情况 | 同工作区？ | 理由 |
|---|---|---|
| 三个老师讲八字的视频 + 五份八字 PDF | ✅ | 以后会问"这几家说法差异" |
| 一份八字资料 + 一份小说稿 | ❌ | 永远不会一起问 |
| 互不相关的几份 PDF | ❌（或「杂项」） | 共同点只是"都是 PDF"，不是用途 |

**格式不是分类依据。** 三类（A/B/C）是"怎么处理"，不是"归到哪"。

**反模式**：不要按"今天投的"建工作区（「Day1-视频」「Day2-PDF」）。三个月后一堆 3 个文件的工作区，检索全废。

### 6.2 硬规则

| 规则 | 内容 | 理由 |
|---|---|---|
| 一个文件一个家 | `source.workspace_id` 非空；要两边用就**复制文件**，不要共用一行 | 归属模糊 → 只有一边触发重索引 → 库与文件不一致，最难查 |
| 批次 ≠ 归属 | `batch` 只记"这一次操作"，`source` 各自带 `workspace_id` | 允许"一批投 5 个，3 进八字 2 进小说"，撤销仍按批次 |
| 对话有唯一的家 | `conv.workspace_id` 必填；跨区是 **`msg` 级参数** | 对话不分裂，上下文不丢，但这一次可以看两个区 |
| 投料不是对话 | 投料是后台动作，不需要开对话等 | 视频转写 10~30 分钟，不该占着会话 |

### 6.3 文件放哪

```
项目内（必须备份）                  项目外（原有目录，别搬）
db/corpus.db                          D:\资料\八字\...
  ├ 索引（可重建）                     E:\写作\小说\...
  ├ 对话（不可重建）                  只登记 path + hash
  └ 记忆（不可重建）
data/workspaces/八字.json
  └ {"roots": ["D:\\资料\\八字"], "config": {...}}
```

**索引可重建，记忆不可重建** → 所以记忆必须在项目内、必须进备份。
**原件不要搬进项目**——那是 A 级整理的活，别抢。

## 7. 投料规则与评测

### 7.1 投进去 ≠ 问得出

投料有两个指标，只有一个自动可得：

| 指标 | 怎么看 | 谁保证 |
|---|---|---|
| **块数**（成功） | 回执里直接有 | 系统自动 |
| **命中率**（有效） | 必须有题去问 | **只能靠评测** |

**块数正常，不代表抽得对。** 这就是为什么投料必须配评测。

### 7.2 四种静默失败（都不报错）

| 失败 | 现象 | 在本项目里会怎么发生 |
|---|---|---|
| 抽不到字 | 库里 0 块，但 `source` 记录存在 | 扫描版 PDF，`pypdf` 返回空文本（见 `text_pdf_module_design.md` 的 `text_pages==0` 提示） |
| 抽错字 | 有字，但搜不到 | ASR 把"七杀"转成"七沙"、人名全错 |
| 切碎 | 命中半句 | `text_splitter` 按字数切，一句话被拦腰截断 |
| 重复 | 召回全是废话 | 视频转写的口头重复，同一段进了 5 个块 |

这四种**没有任何一种会在投料时报错**。三个月后你发现库是垃圾，已经不知道是哪天投坏的了。

### 7.3 规则：投一批料，配 3~5 个验收问题

> **投完一批，立刻问"这批料应该能回答的问题"。答不出来 → 当场修，别等。**

例：投 3 个八字视频 → 立刻问"这个老师主张先看什么" → 答不出或答错 → 5 分钟能定位是转写错字还是切块问题。

**评测不是额外的工程，是投料的最后一步（验收单）。**

### 7.4 极简评测：第一版 20 行，不需要算法

```json
[
  {"q": "违约金怎么算",      "expect_file": "XX合同.pdf"},
  {"q": "这个老师先看什么",  "expect_file": "视频1.mp4"}
]
```

| 阶段 | 做法 | 什么时候升级 |
|---|---|---|
| **1. 打勾** | 跑一遍，人工看答案对不对 | 起步就用这个 |
| 2. hit@k | 算出"命中前 k 条"的比例 | 题量过 50，或开始怀疑"变差了" |
| 3. 回归 | 每次加格式/换模型前后各跑一次 | 有指标以后 |

**别一上来就做框架。** 20 个问题 + 一个脚本 + 一列勾，就够支撑"变好了没有"这个判断。

### 7.5 投料的可运维件

| 机制 | 作用 |
|---|---|
| 回执 | 3 个视频 / 42 分钟 / 1.2 万字 / 86 块 / 主题：XX / 能回答哪类问题 |
| 批次撤销 | 投错了整批删：`batch` → 级联 `source` / `chunk` / `vec` |

回执是"它读过了"的唯一可见证据；技术上只是索引 + 一次摘要。

## 8. 两层记忆

### 8.1 全局记忆：5 条，多一条都算分错

| # | 内容 | 例子 |
|---|---|---|
| 1 | 回答风格 | 先结论后理由；必须带出处；不超过 500 字 |
| 2 | 语言与符号 | 中文为主；英文术语保留原形 |
| 3 | 跨域通用词表 | 甲方 / ROI / KPI / deadline / 交付物 |
| 4 | 安全偏好 | `edit` 必确认；dry-run 默认开；快照留 20 份 |
| 5 | 晋升结论 | 初始为空，只在用户明确说"这条通用"时生长 |

**上限思维：全局超过 50 条，说明有东西该下沉到局部。**

### 8.2 局部记忆：4 类

| # | 类型 | 八字区 | 小说区 | 写入时机 |
|---|---|---|---|---|
| 1 | 术语 | 七杀 = 偏官 | 人名 / 地名 / 门派 | 索引后批量 |
| 2 | 纠正 | "不是大运，是流年" | "这个人物不叫阿七" | **当场写** |
| 3 | 偏好 | 导出 docx，引原文 | 导出 md，人物一致 | 第 2 次重复时 |
| 4 | 结论 | "这位老师先看月令" | "第三章倒叙" | 用户说"记住"时 |

### 8.3 界线与写入原则

| 问题 | 判断 |
|---|---|
| 换到别的工作区还成立吗？ | 毫不犹豫成立 → 全局；**犹豫 → 局部** |
| 是"怎么做事"还是"这件事是什么"？ | 怎么做事 → 全局；这件事是什么 → 局部 |
| 没有明确信号要不要写？ | **不写**。记错比不记更难修（得先发现它记错了） |

**继续守 `dev_log` 里定的"不做自动学习"。**

### 8.4 跨工作区的三级阶梯

| 级别 | 做法 | 有效期 | 场景 |
|---|---|---|---|
| 临时 | 这次提问带两个工作区 | 关掉就散 | "对照一下这两边" |
| 引用 | 写入 `ref` 表 | 长期 | "这个结论出自那本书" |
| 晋升 | 提为全局记忆 | 永久 | "这条对所有工作区都成立" |

**大部分跨区需求第一级就够。** 预建的跨库链接十有八九用不上。

**跨区必须按来源分组，冲突要明说**：同一个词在两个区不同义（"七杀" / "甲方"），不许静默合并——否则模型一会儿按命理答、一会儿按剧情答，且无法解释。

## 9. 工具划分：7 个，到此为止

| # | 工具 | 参数 | 破坏性 | 成本 |
|---|---|---|---|---|
| 1 | `search` | q + 工作区 + k | 无 | 0 token |
| 2 | `read` | 块 id / 路径 + 范围 | 无 | 0 token |
| 3 | `ask` | q + 工作区 + 目标 | 无 | 有 token |
| 4 | `ingest` | 文件 + 工作区 | 只写库 | 抽取（ASR 最贵） |
| 5 | `organize` | 目录 + 规则 | 移动文件 | 0 token |
| 6 | `edit` | 路径 + ops | **不可逆** | 有 token |
| 7 | `generate` | 内容 / 来源 + 目标格式 | 新文件 | 有 token |

### 9.1 两条分界线

1. **改现有文件 → `edit`；产出新文件 → `generate`。**
   PDF 删页/旋转归 `edit`；拆分/合并/提取页归 `generate`（虽然合并吃多输入，但产物是新文件）。
2. **0 token 的原子操作（`search`/`read`）与有 token 的合成操作（`ask`）分开。**
   成本差一个数量级，模型应能主动选便宜的。

### 9.2 被合并掉的候选

| 候选 | 归到哪 | 为什么 |
|---|---|---|
| `summarize` | `ask` | 输入形状相同、失败后果相同 |
| `export` | `generate` | 都是"产出新文件" |
| `inspect` | `read` | 只读结构就是读 |
| `ocr` / `vision` / `asr` | `read` 内部适配器 | 模型不该判断"这文件要 OCR 还是抽文本层" |
| `word_office` / `text_office` / `pdf_office` | `edit` 的 op 变体 | 格式是参数，不是工具 |

**加视频 / 图片 / PPT，这张表一行不动。**

### 9.3 现有代码的归属映射

| 现有 | 归到 |
|---|---|
| `table_query` / `table_synthesize` | 查询走 `ask`，出表走 `generate` |
| `word_office`（11 op） | `edit` |
| `text_office`（7 op） | `edit` |
| `file_organize` | `organize` |
| `scan` / `parse` / `classify` / `split` / `ai_call` / `analyze` | `read` / `ingest` 内部 |
| `export` | `generate` |
| `review` | 内部机制，不是工具 |
| `vision`（现为降级标注） | `read` 内部适配器 |

### 9.4 三个计划槽位（别漏第 0 条和第 4 条）

实际要做的是四条，不是三条：

| # | 内容 | 说明 |
|---|---|---|
| **0** | **决策层**：AI 怎么选工具、何时问人、失败怎么退 | 已有（路由 + DAG + 门禁 + 确认），**别在总结里丢掉** |
| 1 | 格式落地 + AI 调用 + 基础增删查改 | 写面，留在 filemate |
| 2 | 本地感官：OCR / ASR / **embedding** | embedding 不是"识别"，是"索引"，但同属本地模型 |
| 3 | 库 + 两层记忆 + 跨区联动 | 地基，最先做 |
| **4** | **评测**：每批 3~5 问，一个 json + 20 行脚本 | 不是第四件事，是 ②③ 的验收方式 |

连接件两个：**写后 reindex**（1 → 3）、**批次撤销**（3 的运维）。

## 10. 写面与读面的调用规则

> **写工具不许自己打开 PDF / MP4 / 图片。它只吃 `text + locator`。**

- 写工具需要内容 → 调 `corpus.read(path)`，不自己解析；
- 内部按 `hash` 缓存，同一文件第二次读几乎免费；
- 已在库里索引过的，直接查库，连文件都不用打开。

**写后重识别（reindex）**：`edit` 成功后自动触发——
算新 hash → 变了就删旧块重抽 → 没变就跳过（只改样式的情形）。
不重索引，库与文件就不一致：改了合同违约金，问答还是旧数字。

## 11. MCP 的定位：出口，不是架构

| 项 | 结论 |
|---|---|
| 解决什么 | "谁能调用你的工具"——Claude Desktop / Cherry Studio / 别的 agent |
| 不解决什么 | 库分区、记忆分层、跨区串味、工具划分 |
| 形态 | **一个 server，多个工具，工作区当参数**；不要每个工作区一个 server |
| 何时值得 | 需要外部客户端调用时；只在自己 PyQt 里用 → 多一个进程边界，收益为零 |
| 必须先解决 | **危险操作两段式确认**：首次返回 `needs_confirmation + token`，带 token 的第二次调用才执行（MCP 里没有"用户"这个概念） |

内部先有工具注册表（schema 化），MCP 只是把同一张表导出。

## 12. 仓库策略与封版

### 12.1 按"面"拆，不按"功能"拆

| | filemate（敲门砖） | 新仓库（长期工具） |
|---|---|---|
| 职责 | **写面**：Word / Excel / txt 的深操作 | **读面**：库 + 工作区 + 两层记忆 + 感官 |
| 已有什么 | 契约 + 七状态机 + 快照 + 门禁 + 11 个 op | 从零，结构见本文档 |
| 目标 | **冻结、讲得清、能演示** | 每天用、慢慢长 |
| 不做 | 不再加格式 | 第一版不做"改原文件" |
| 交接点 | 导出文件（`generate`） | 读文件（`extract`） |

**为什么这么拆**：写面和读面本来就只在 `corpus.read()` 一个点相接。按面拆，不复制代码，两边都完整；按功能拆（新项目把三条全做一遍），会得到两个半成品。

### 12.2 允许 fork，禁止双活

> **可以复制，但必须"一个冻结、一个活跃"。双活 = 三个月后 40k 行 × 2，且不知道差异在哪。**

三条操作细节：

| 项 | ❌ 别这么做 | ✅ 这么做 |
|---|---|---|
| 复制方式 | 复制文件夹（丢 commit 历史） | **`git clone`**，保留历史（"你怎么迭代"的证据就在里面） |
| 冻结标记 | 口头说"不再改了" | **`git tag v1.0-portfolio`** + 打包一次，随时能 checkout 演示 |
| 新仓库 | 留着 `origin` 指向公开仓库 | **第一件事 `git remote remove origin`** + 建私有仓库 |

**冻结之后只允许两类改动：安全修复、依赖升级。任何新功能都不许进。** 一旦"顺手改一下公开的那个"，就变双活了。

### 12.3 封版条件（敲门砖必须"完成"才值钱）

> 一个永远在施工的项目，在面试里不如一个小而完整的项目。

| 项 | 标准 |
|---|---|
| 格式 | 3 个（word / txt / excel），**不再加** |
| 深度 | 11 op + 七状态机 + 写前快照 + 失败整包还原 + 证据链 |
| 测试 | 全绿（现有 138 个测试文件先跑绿并提交） |
| 文档 | README 里一节「设计取舍」：为什么契约驱动、为什么线性链、为什么 v4 不做 |
| 演示 | 3 分钟录屏：一句自然语言 → 改一份 Word → 失败能回滚 |
| 加分项 | 一份「我放弃过什么」清单：v4、自动学习、pytest-qt |

**最后一项比格式数量值钱十倍**——能讲清"为什么不做什么"，是高级工程师和"会堆功能"的分界线。面试看的是技术判断，不是格式数量。

### 12.4 修正后的整体计划

```
filemate（敲门砖）              新仓库（长期）
  写面 · 封版                    读面 · 从零
  word/excel/txt                 corpus + workspace + memory
  契约 / 状态机 / 快照             extract + index + ask + 评测
  3 分钟能讲完                    每天用，慢慢长
        └──────── 交接点：导出 / 读取文件 ────────┘
```

| 阶段顺序 | 理由 |
|---|---|
| 3 库 → 2 感官 → 1 格式 | 库是地基；没有库，感官无处可放，格式也无处可查 |
| 4 评测贯穿 | 每批投料、每次换模型都跑；它验证 2 和 3 |

## 13. 被否决的方案

| ❌ 否决 | 理由 |
|---|---|
| 为新格式另开一个"重写版"项目 | 抽取器 / 库 / 评测必须共享，否则必然漂移（已有双份状态机的前车之鉴） |
| 按"功能"拆仓库（新项目把三条全做） | 得到两个半成品；应按"写面/读面"拆 |
| **复制文件夹另开仓库** | 丢 commit 历史；且极易变双活 |
| **两个仓库都活跃** | 两边都改，三个月后无法判断差异从哪来 |
| 按格式分工具 | 7 格式 × 7 动作；且模型分不清"读 PDF"和"读 Word" |
| 每个工作区一个 `.db` | 跨区查不了、备份 N 份、schema 升级跑 N 次、全局记忆无处安放 |
| 加一层"工作区组" | 个人用不到；且会变成第三种边界。要么合并工作区，要么晋升全局，没有中间态 |
| 一份文件属多个工作区 | 归属模糊 → 重索引漏边 → 库与文件不一致 |
| 全局记忆放具体事实 | 那是素材不是记忆；三份合同各有各的事实 |
| 自动写记忆 | 记错比不记更难修 |
| 微调（LoRA） | 需重训、不能引用、无法验证、个人量级 RAG 更强 |
| 用对话做分类 | 三个月后一堆"新对话"，什么都找不回 |
| 为工作区做管理 UI | 给还不存在的需求做界面，是个人工具最大的浪费 |
| 投料不做评测 | 块数正常 ≠ 抽得对；四种静默失败都不报错 |

## 14. 落地顺序

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **0** | **冻结本文档的划分**；filemate 提交 + 跑绿 + 封 tag | 无 |
| 1 | `corpus/schema.py` + `corpus/ingest.py`（回执 + 批次撤销） | 阶段 0 |
| 2 | `corpus/read.py`（docx / pdf / txt / xlsx → 统一 `text + locator`） | 无（可复用 `file_parser`） |
| 3 | `ask`：检索 → 模型 → 带出处；输出接现有 `export` | 阶段 2 |
| 4 | **投料验收**：20 题 + 每批 3~5 问 | 阶段 3 |
| 5 | 加格式：PDF 只读 → 图片 OCR → 音频/视频 ASR（每加一个跑一次评测） | 阶段 2、4 |
| 6 | 本地 embedding（`ai/embed.py` 改成可配 `base_url`） | 阶段 3 |
| 7 | `conv` / `msg` 表 + 对话归属 | 阶段 5 |
| 8 | MCP 导出（可选） | 阶段 7 |

**顺序理由**：库是地基；评测在加格式之前，否则无法判断"变好了没有"；MCP 最后，因为只有外部调用时才付协议成本。

## 15. 已知风险与边界

| # | 风险 | 现状 / 对策 |
|---|---|---|
| 1 | FTS5 中文分词：`memory.py` 建表未写 `tokenize=`，默认 `unicode61` 把整句当一个词，`MATCH` 基本失效，故旁挂 `_like_hits` | 三条路：`trigram`（2 字词失效）/ jieba 预分词 / 保持 LIKE（几千块够用）。**个人库先不优化** |
| 2 | 小说不能只按 512 字切 | 需"章节摘要 → 场景块"两层索引 |
| 3 | 八字排盘是**计算**不是检索 | 归工具层（确定性代码），不塞进库；能算的别让模型猜 |
| 4 | 视频只承诺"转写 + 关键帧" | 纯画面理解要 VLM，贵、慢、本地跑不动；不承诺"看懂视频" |
| 5 | ASR 是唯一重活 | i5-10400 CPU + faster-whisper small ≈ 10~15 分钟/小时音频；6650 XT 在 Windows 上帮不上（CTranslate2 只支持 CUDA） |
| 6 | 旧四套记忆不迁移 | 新库从零索引，旧的继续跑，稳定后逐个掐掉 |
| 7 | 写面接口未统一 | `word_office` 未迁 `office_core`；`list[Path]` 签名改造是阶段 0 之外的已知欠账（见 `text_pdf_module_design.md` §11） |
| 8 | 工作区由人选，不由模型猜 | 模型只允许在工作区**内部**决策；跨区必须显式 |
| 9 | 评测流于形式（只投不验） | 每批投料强制配 3~5 问；第一版只打勾，不追求指标 |

## 16. 自审

| 项 | 结论 |
|---|---|
| **矫枉过正** | 否——7 个工具封顶、全局 5 条、评测 20 行、只做 A/B/C 三类，都是砍到最小 |
| **违背初衷** | 否——个人工具：不做微调、不做工作区组、不做管理 UI、不迁移旧记忆 |
| **技术利弊** | 利：加格式只加 `extract()`，读面共享一套索引；弊：中文分词要单独治，视频转写要等，跨区冲突要显式处理 |
| **与现有架构冲突** | 否——写面（`office_core` / `word_office`）不动；读面新增平级包，不 import Qt / dispatcher / 契约 |
| **未决项** | ① 视频类型（讲课/教程）决定要不要做关键帧 OCR；② 是否真的需要 PDF 页级写 |

## 17. 一句话

**一个库（8 张表，按工作区分区）、7 个工具（格式是参数）、两层记忆（全局记"怎么做事"，局部记"这件事是什么"）；三件事各改一个东西——投料改库、问答什么都不改、操作改文件；评测是投料的验收单；两个仓库一冻结一活跃，冻结的那个只修安全和依赖。**
