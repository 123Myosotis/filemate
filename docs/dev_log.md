## 2026-11-17 修：成稿清单累计进 storage

**初衷对照**：docx / xlsx 是给人看的交付物，不是状态库；累计不能靠反读清单，更不能依赖「>500 才出 xlsx」。

### 回归

- Word 化后 `_load_fill_manifest_rows` 只读 `成稿清单.xlsx`（常规 ≤500 不存在）与旧 `_成稿清单.md`（首轮后已删）。
- 连续两次模板填槽 → docx 被覆盖成仅本轮 1 行；旧 md 是追加的，行为倒退。

### 操作

- 累计行改存 `storage/content_index/<uuid>/fill_rows.json`（`state.cache_path`）。
- 每轮：读 storage → 追加 → 原子写回 → 再 `write_table_report` 生成展示用 docx/xlsx。
- 首次若无 storage：一次性从旧 xlsx / `_成稿清单.md` 迁入。
- 消息「清单：…」改用实际写出文件名（含占用时间戳 / 超 500 的 xlsx）。
- 测：`test_fill_manifest_accumulates_across_runs`。

### 利弊与自审

- **利**：≤500 也能跨轮累计；500 阈值与占用另存不影响历史。
- **弊**：`模板成稿/` 也会有 `.filemate/id`（与内容分类同一目录身份机制）。
- **是否违背初衷**：否——状态进项目 storage，交付物只展示。
- **是否偏离架构**：否——复用既有 `state.cache_path`，不另起一套路径。
- **未改**：拆分清单仍每轮新集合（语义正确，不累计）。

## 2026-11-17 内容分类：状态进 storage + 通用 Word 清单

**初衷对照**：输出目录只放用户要看的类目 + 清单 + 隐藏 `.filemate/id`；索引/缓存进项目 `storage`，不污染用户文件夹。仍是「另存新文档」，不做搬家、不做后台 GC/多进程锁。

### 1. `pipeline/content_split/state.py`

- **操作**：`dir_id` / `index_path` / `cache_path` / `load_index` / `save_index` / `_migrate_legacy`；`FILEMATE_CONTENT_STATE_DIR` 可改 storage 根。
- **改名 vs 复制**：root 不一致时，若旧路径仍在且同 UUID → 复制，换新 UUID；否则视为改名/移动，更新 root、索引继续有效。
- **利**：目录身份与绝对路径解耦；复制互不覆盖；测试可隔离。
- **弊**：删输出目录后 storage 成孤儿（几十 KB）；清理入口以后再做。复制后旧 UUID 目录残留同理。
- **风险（记录）**：同目录多进程 last-write-wins，本刀不加锁。

### 2. 接入点（只动约定三处）

- **batch_new_docs**：`_load_index_payload` → `state.load_index`；`_save_hash_index` → `state.save_index`。无索引不再标 stale（删 id/storage/换 UUID 后按磁盘重建、不重复写）。
- **soft_label**：缓存路径 → `state.cache_path(..., label_cache.json)`。
- **common**：移除 `state_dir` / `migrate_legacy_state`，避免两套状态实现。

### 3. `export/docx_report.write_table_report`

- **操作**：≤500 → 仅 docx；>500 → xlsx 全量 + docx 摘要（前 100 行）；列≥7 横向；临时文件 + `os.replace`；占用 → 时间戳副本并返回实际路径。
- **分类清单**：batch 只提供列 schema，版式走通用入口。
- **利**：后续整理/模板/跨表清单可复用，不再各写一套 Word。
- **弊**：xlsx 依赖 openpyxl（项目已有）；摘要行数固定 100，大表仍要打开 xlsx。
- **未做**：其他清单接入、清理缓存 UI、文件锁。

### 4. 测试

- conftest 固定 `FILEMATE_CONTENT_STATE_DIR`；`test_content_state`（首次/改名/复制/删 id/删 storage/迁移）；`test_docx_report`（500 阈/占用另存）；旧用例改读 storage 索引。

### 5. 自审

- **是否违背初衷**：否——用户目录更干净；状态归属项目 storage。
- **技术利弊**：见上；改名靠「旧路径是否仍挂同 id」区分复制，极端并发下两副本同时存活才 rotate（符合「复制」语义）。
- **是否偏离架构**：否——仍 content_split 管业务，export 只管报告写出；未引入 Web/守护进程。

## 2026-11-14 .doc 宏安全 + 失败细分 + 规则指纹锁

**初衷对照**：打开用户文档不得执行宏；失败原因要可行动；清单不得「类型与得分打架」；改规则忘升版本会锁死旧错分——必须有机械检查。

### 1. 宏安全（P2）

- **操作**：`app.AutomationSecurity = 3`（ForceDisable）后再 `Documents.Open`。
- **利**：降低 AutoOpen 宏风险；只读不够。
- **弊**：极少数依赖自动化宏才能打开的受保护文档可能变 `open_failed`（可接受）。

### 2. 失败原因颗粒度（P3）

- **操作**：拆 `com_unavailable`（Dispatch 失败）/ `open_failed`（打开/策略）/ `encrypted` / `corrupt`；清单脚注写明。
- **利**：不再把「Word 被禁用」误标成文件损坏。

### 3. 空目录（P3）

- **确认**：本轮结束后 `_cleanup_empty_type_dirs` 仍会清「内容分类/<类目>」空壳（此前已接）。

### 4. 强制报告清单观感（P3）

- **操作**：判别类型列 `报告〔结构强规则〕`；得分列前缀 `〔结构强规则→报告〕规则分 …`；目录名仍纯「报告」。
- **利**：一眼能看出强制，不再像「技术 11 赢了却写成报告」。

### 5. `RULES_DIGEST` 绑定（流程）

- **操作**：`compute_rules_digest()` + 硬编码 `RULES_DIGEST`；单测断言相等。改 FEATURES/置信/强规则必须：`CLASSIFIER_VERSION+=1` 且刷新 digest。

- **弊**：合法小改也要动两处（故意，防止漏）。

## 2026-11-14 分类索引 stale 覆盖 + 报告强规则（v3）

**初衷对照**：规则升级要重算，但绝不能「越修越复制」；用户目录里同一内容只应有一份成稿。错分改正 = 覆盖/换夹，不是再堆 `_1`。

### 1. 版本失效 → stale 重算（P1）

- **操作**：索引条目改为 `{rel,label,doc_type,top2,stale}`；版本不一致时**重建索引并标 stale**，不丢路径。命中 stale：同类 `copy2` 覆盖旧副本；换类只删索引登记的旧文件再写新夹；**不走 unique_dest**。`CLASSIFIER_VERSION=3`。
- **初衷**：修规则是为正确，不是制造重复垃圾。
- **利**：桌面 15 篇再跑不会再多 15 份。
- **弊**：换类时若新夹已有同名无关文件会被覆盖（仅 stale 迁移路径；全新文件仍 unique_dest）。
- **架构**：仍只动「内容分类/」输出树，不碰原件。

### 2. 报告结构强规则（P1）

- **操作**：前 500 字命中 `实训报告|实验报告` 且结构词 ≥2 → 强制 `report`（`forced_report`）。
- **利**：技术词密度高的实验报告不再输给 technical。
- **弊**：极个别「引用实验报告」的非报告文可能误伤（门槛要标题+结构，风险可控）。

### 3. hash 跳过回填判别（P2）

- **操作**：非 stale 跳过时清单回填索引里的 label/doc_type/top2。
- **利**：看起来不像「没识别」。

### 4. legacy_word finally（P2）

- **操作**：`doc=None`；finally 先 `Close(False)` 再 `Quit`，降低残留 WINWORD。
- **说明**：两份 `.doc` 仍需本机 `pywin32`+Word，或用户另存 docx——代码侧已就绪，环境未装则继续明示跳过。

### 5. 测试

- 已有产物版本升级不产生 `_1`；换类删旧；hash_skip 回填；技术密度报告仍强制 report。

## 2026-11-14 分类器 v2 + Word 老格式（A+B）

**初衷对照**：规则可解释、零成本优先；错分要能靠版本号强制重算，不能被 hash 永久锁死；`.doc` 不静默漏掉；不擅自改用户文件格式；不执行宏。

- **初衷**：目录仍是固定枚举，不是自由标签。
- **利**：实验报告/剧本/规格说明与小说脱钩。
- **弊**：边界文（产品设想）仍可能 technical/project 摇摆；靠文件名加权补。

- **操作**：`scale=1000/(n+500)`；文件名 boost；`top1<1.0` 或 `margin<0.8` → other；`<500` 字另要求 `margin≥1.0`。
- **利**：短文虚高下降；文件名高精度零成本。
- **弊**：极短合同可能进 other（可接受，宁漏勿错）。

### 3. `CLASSIFIER_VERSION=2`

- **操作**：写入 `_content_hash_index.json` / `_label_cache.json`；版本不一致 → 空索引/空缓存强制重算。
- **利**：规则升级后旧错分不会被 hash_skip 永久保留。
- **弊**：升级后可能产生与旧目录并存的新副本（不自动删旧夹，避免误删用户整理）。

### 4. `.docx/.docm/.doc` 扫描

- **操作**：`WORD_EXTS`/`LEGACY_WORD_EXTS`；清单加「格式」列；`.docm` 当 zip 抽文本并记 `macro_docm`；`.doc` 默认 A 跳过 `legacy_doc_no_converter`，有 pywin32+Word 走 B（COM 只读转临时 docx）；输出仍复制原件字节。

- **弊**：未装 Word/pywin32 时两份老合同仍要用户另存；COM 启动有成本（按需才调）。
- **架构**：转换隔离在 `legacy_word.py`，不进 WordOffice 润色链；LibreOffice 路径未做（按建议顺序暂缓）。

### 3. `find_by_tag`（优先级 3）

- **操作**：`WHERE tags_json LIKE ?` 收窄后再精确匹配；`require_alive` 跳过并删除失效 path。
- **利**：库大时不被「先 LIMIT 500 再过滤」截断老记录；结果可点开。
- **弊**：LIKE 是粗筛，极端多标签共前缀时多扫几行（可接受）。

### 4. 软标签配额（优先级 4）

- **操作**：非 `cache` 的软标签结果一律 `soft_model_calls += 1`（含 `fallback_error`）。
- **利**：模型连失败也不能无限打。
- **弊**：合法 cache 命中不计次（故意）；无 Key 不进软标签分支。

### 5. 首次自动回填（优先级 5）

- **操作**：`content_tags_meta` + `ensure_auto_backfill`；分类启动与「按标签找」前自动一次；「回填标签」`force=True`。
- **利**：老产物无需先手动口令即可搜。
- **弊**：按目录绝对路径记 meta，换盘符/换工作区会再回填一次（幂等，可接受）。

### 6. 测试

- 模板：表格槽 + 段落样式名保留；标签：死路径修剪、自动回填 once、失败占配额；conftest 隔离。

## 2026-11-12 裁定：两套记忆要不要换？

**问题**：Excel `memory_rag` 与 Word `memory.py` 分开，是不是「不完善」？要不要合成一套？

### 自审（初衷 / 利弊 / 架构）

| 维度 | 判断 |
|---|---|
| **初衷** | 本地优先、记忆不碰业务文件、Excel≠Word。合成一张表会逼两边共用键模型，容易把「列名/绑定」和「段落锚点」搅在一起 → **违背「不无视 Excel≠Word」**。 |
| **架构 §8–§9** | 复用原则是「先比对，能抄格式就抄，不能复用就独立」；红线是 **Excel 代码不能碰**、**不能为复用而扭曲**。两套 = 已按文档落地，不是临时债。 |
| **利** | ① 表格侧重 join/口径/术语↔列；文档侧重文件主题/术语↔段锚/即时会话——失败域隔离。② 改 Word 召回不会拖垮跨表 QP。③ 向量/FTS 策略可按域不同（Word 小库全量、Excel dense 另一套）。 |
| **弊** | ① 两套表、两套 API，学习成本高。② 同一黑话在表里和文档里可能各记一份，不会自动互通。③ 运维要清两次库。 |
| **换一套的代价** | 大重构 + 必动 Excel 记忆路径 + 回归面是整条跨表链；收益主要是「代码好看」，不是能力变强。**不划算**。 |

### 操作（本条只裁定，不改代码）

- **裁定**：保持两套；格式/生命周期可继续对齐抄，**禁止**合成存储。
- **写入**：`docs/architecture.md` §9 加裁定句；本日志备案。
- **不做**：合并库、统一 ORM、让 Word 直接 import `memory_rag` 写表。
- **可做（以后，仍非合并）**：文档里画一张「抄了什么 / 没抄什么」对照，减少新人误会「漏做了统一小脑」。

## 2026-11-19 战略评估：如果加图片识别，项目会变成什么

**性质**：只做判断，不改代码。用户原话：想加图片识别，但觉得"烂大街、没突出"。

### 先拆词：图片识别是 4 件不同的事，价值差一个量级
| 形态 | 价值 | 是否与本项目契合 |
|---|---|---|
| 通用图片描述 / 分类 | 低（市场已饱和） | 否，属于"加功能" |
| **扫描件 PDF 的 OCR** | **高** | **是，直接补 `pdf_office` 已声明的最大缺口** |
| **截图/照片表格 → 表格数据** | 中高 | 是，接 `table_query` 跨表链路 |
| 图片按内容归档 | 中 | 是，`file_organize` 的自然延伸 |

### 预判：两个分叉
- **B 路线（加功能）**：Word + Excel + Text + PDF + Image + … → 变成"万能格式处理器"，**靠广度竞争**，正是用户担心的"没突出"。
- **A 路线（补缺口）**：图片只用于"补文本层"（扫描件 OCR）与"补表格入口"（截图表格）→ 项目仍是"**本地优先的文件加工台**"，只是链路更完整。

### 真正可能的差异化（不在"能识别"，在"识别之后"）
1. **本地优先 / 数据不出机**（但云 vision 会破坏这一点，需明确开关与告知）；
2. **可回滚、可审计、有证据**（`office_core` 已有，市面 AI 应用普遍没有）；
3. **批量 + 接入既有数据链路**（识别结果直接进表格/文档/归档，而不是一次性问答）；
4. **确定性层零 token**（无 Key 也能用）。

### 架构代价（若真做）
- Vision 是"读"能力，**不产生 patch** → 不能套 `office_core` 的 verify/回滚模型，应定位为"读 + 建议"，不写回；
- 云 vision = 图片外发，与"证据只落本地、不上传"的承诺**冲突**，必须先做外发告知/开关；
- 本地 OCR（tesseract/paddle）是重依赖 + 中文/表格准确率参差；
- 会**加剧范围蔓延**（12 阶段路线图尚未开工）。

### 结论
- 用户的直觉**对一半**：通用识图确实没差异化；
- **唯一值得做的两刀**：扫描件 PDF OCR、截图表格导入；其余不做；
- **判断标准不是"市场有没有"，而是"你手头有没有 100 个扫描件/截图表格要处理"**——没有就别加。

## 2026-11-19 战略问答：个人项目在 AI 时代的价值（用户提出"有 DSH 等，我这种个人项目没什么用"）

**性质**：只做判断。用户澄清：加图片是为了"之后往深度走"，因为广度比不了；并质疑个人项目存在意义。

### 我的回答要点（存档）
1. **分两个尺度回答"有没有用"**：对市场（做成产品）→ 很难；对自己（工具化工作流）→ 站得住。
2. **跟 DSH 类通用 Agent 对比**：输在"通用能力/模型/分发"；不输在"你的文件、你的格式、你的记忆、你的回滚/审计"。通用 Agent 每次都从零开始，你的项目是**已接线的胶水**。
3. **"深度"要定义清楚**：深度不在"格式数量"，在**一条链路做穿**（识别 → 提取 → 分析 → 报告 → 归档 → 记忆）。
4. **残酷判断标准**：这个工具三个月内有没有把你的某件重复劳动从 2 小时压到 5 分钟？没有就是没价值。
5. **加图片 ≠ 深度入口**：图片只是补 PDF/表格的缺口；它不会自动带来"深"。

### 结论
- 用户的直觉"广度比不了、该走深度"**是对的**；
- 但"个人项目有没有用"取决于**用途定义**，不取决于市场新意；
- 建议：停止加格式，选定一条链路做穿，用"是否省下时间"作为唯一验收。

| 项 | 结论 |

| 技术利弊 | 利：聚焦；弊：需承认"个人项目不是产品"，且 AI 正在蚕食胶水层，时间窗口收窄 |

## 2026-11-19 计划评估：用户打算"先把功能补全，再回头读代码"

- 每加一个功能，必须能回答"**它接在哪条链的第几环**"，否则不允许加下一个。

### 主链路地图（本项目实际）
`main.py` → `ui/main_window.py` → `engine/dispatcher.py::dispatch` →（tool 分流）
→ `agent_core/intent_router.py`（选 tool）
→ `pipeline/word_office/module.py::WordModule.handle`（或 `office_core/runner.py`）

→ `_execute`/`_exec_*`（或 `adapter.execute`）→ verify → `evidence` → `memory`
→ `_finish`（七状态机）→ 返回 UI

1. **画一张图**：一次请求从输入到落盘的完整流；
2. **走一条链路**：选 `find_replace`，用断点/日志跑一遍，看每层的入参出参；
3. **再走一条不同 tool**：`file_organize`，看**共享层**如何复用；
4. 每层只答 3 个问题：**它从哪拿数据、它改了什么、它失败怎么退**。
